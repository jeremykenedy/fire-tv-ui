# Cross-module launcher behavior review

Scope: current maintained source for Main, folders, app-grid preferences, locks, Quick actions, recommendations, notification actions, TV inputs and presentation snapshots. Read-only except the coordinator explicitly approved the folder focus/identity fixes and app-grid discovery helper below. No device input, APK build or publication occurred in this review. Native proof is pending; source findings and passing host checks are not hardware acceptance.

## Concrete findings and disposition

1. **Saved Home tile focus was cleared on recreation.** Main restored `focusedApp`, requested Settings focus during creation, then cleared the saved tile in initial `onResume`. This affected app, folder and input tiles. Sent to cards_render, whose integration now includes a `restoringGridFocus` flag that preserves the pending identity through header initialization. Source readback confirms the flag. Native Home tile recreation still needs operator proof.

2. **Recommendation cards bypassed launcher PIN guards.** Main card actions called `RecommendationActions.launchTitle/launchDetails/launchPlay/openApp`, which started activities directly; notification content actions also sent their PendingIntent without guarding the publisher. Normal Home UI could reach an app locked from the ordinary app grid. Sent to provider_actions and app_locks. Current source now guards the resolved publisher launch component and explicit destination; opaque notification routes guard a locked publisher component before sending. It revalidates explicit destinations after authorization. Source readback confirms the repair, but route/PIN native proof remains pending. The new asynchronous `PENDING` outcome must not trigger Main's unavailable toast; this integration detail was sent to the provider owner and coordinator.

3. **View-only app discovery materialized unrelated absent defaults.** Main previously saved a complete `AppGridOptions` snapshot after every inventory read. This wrote absent columns, rows, direction, hidden and favorites keys merely by opening Home or returning from a presentation restore. With explicit coordinator approval, added `AppGridPreferences.saveDiscoveredOrder(Context,List<String>)`, which writes only changed order, leaves all other absent/explicit keys intact, keeps missing components, rejects malformed existing order and rolls back failed commits. Coordinator reports Main helper/catch integration is wired. Full save remains unchanged for explicit user controls. Focused host checks pass, including absent-order rollback and no redundant commits.

4. **Folder recreation lost the nonfirst focused member.** Initial manager rendering overwrote the saved member key before the requested folder was reopened. With coordinator approval, `FolderActivity` now carries the saved key explicitly through initial safe manager rendering and lock authorization. Native proof now selects the second member before recreation and checks it is restored. Isolated Android compilation passes; operator execution remains pending.

5. **Short component aliases differed from full inventory/lock keys.** FolderOptions accepted `package/.Main`, but the Activity searched inventory by full component string and incorrectly showed that accepted member as unavailable. Coordinator authorized canonicalization in FolderOptions. Construction, add/remove/move now normalize the alias to full class identity, collapse duplicate aliases and keep bounds. Host regressions pass for canonical membership, duplicate handling and alias remove/move. app_locks independently normalized LockState target keys so shortened Quick actions/source keys share full component locks. Quick actions currently uses private device-only storage and GUI-generated full components; there is no claimed portable-import exploit.

6. **Input viewer dispatch needs an explicit lock policy.** InputActions revalidates platform state, resolves an enabled/exported permitted system viewer and dispatches through DeviceRoutes for the Home handoff. It currently does not ask LauncherLocks. If that exact viewer is also an app-grid component the user locked, Open input inside the launcher could reach it without a PIN. Sent to inputs and coordinator for the Activity-aware guard policy while retaining handoff suppression. This is conditional on the device exposing the same system component in both roles; no target-device reproduction is claimed.

## Boundaries checked

- FolderActivity is nonexported. Both manager/direct-folder opening require the folder guard; member dispatch separately requires the app guard. Canceling a folder PIN leaves only the manager, not protected folder contents.
- A successful folder entry remains an Activity session; opening a member still performs its own app lock check. Recreation reauthenticates folder entry. No lock state enters saved instance state, folder preferences, presentation snapshots or portable exports.
- Hidden app state is scoped to the ordinary Home app grid. Existing explicitly selected folder membership and Quick actions remain separately available and still guard app dispatch. No finding assumes that Hide from Home is a system/privacy lock.
- Folder changes never write ordinary app-grid/favorites or uninstall applications. Missing folder members remain visible until explicitly removed. Unsupported legacy folder/app-order values remain opaque; this review adds no speculative migration decoder.
- Quick actions pins HTTPS links to the selected app, guards selected and resolved components, and resolves again after authorization. Generic Android intent strings, system settings actions and non-HTTPS URLs are not accepted.
- Input selection does not treat a successful start as proof that a physical input switched. Missing/disconnected/unavailable states are rechecked and saved names/artwork survive unavailable hardware.

## Bounded app-order capacity follow-up

The combined integration owner identified a deterministic cap failure: 2048 remembered component IDs plus any fresh installed app made `discover` throw; even Main's persistence catch could not protect `visible`, which called the same throwing path. Under the delegated AppGridOptions lease, discovery now fills only remaining remembered capacity and retains every historical ID. Rendering separately appends unremembered current apps in transient inventory order, preserving favorite and hide behavior. Moves involving an unremembered endpoint return unchanged rather than indexing `-1` or discarding an existing identity.

`AppGridOptions.MAX_IDENTITIES` exposes the bound. `unrememberedCount(available)` reports the number of installed apps whose additional order cannot be saved. The integration owner was told to display this capacity state explicitly; fresh apps remain usable and no missing history is silently removed. Focused regressions cover a full history, partial remaining capacity, persistent history preservation/no redundant save, visible overflow apps, favorite/hide behavior, and moves across the overflow boundary. The host app-grid suite and isolated SDK36 model/store compilation pass. Native behavior and capacity message verification remain coordinator work.
